## A parte de QA

O site é a amostra de trabalho, então a engenharia foi feita para ser verificada.

### Todo craft é reproduzível

O motor de crafting é uma **função pura com RNG semeado**. Um craft é descrito por `base + semente + orbes`, então a bancada consegue:

- **Copiar link de reprodução** — abre exatamente o mesmo item em qualquer máquina (`#craft=bug.2a.0458`).
- **Copiar relatório de bug** — um ticket pronto: ambiente (semente), passos numerados incluindo as tentativas que _falharam_, resultado obtido e o link de reprodução.

É a piada de QA levada a sério: o gerador de bug reports abre bug reports sobre os seus bug reports.

### Bugs que esta reescrita encontrou

A versão antiga era JS puro. Reconstruí-la com testes revelou defeitos reais — o tipo de lista que eu entregaria para um time depois de um ciclo de testes:

- A animação de brilho da aura **nunca rodava**: o CSS apontava para `#aura1`, que não existia.
- Os tooltips da árvore usavam um tema e uma animação do Tippy cujo CSS **nunca era carregado**.
- Scripts de CDN **sem versão fixa** (`tippy.js@6`) e sem verificação de integridade.
- `initial-scale=0.6` encolhia a página no celular para esconder um layout de 431px — agora a suíte garante **zero rolagem horizontal** a partir de 320px.
- Erros de crafting apareciam na tela mas **nunca eram anunciados** para leitores de tela.
- Modais eram divs simples: o fundo continuava acessível para tecnologias assistivas.
- Itens salvos **sumiam ao recarregar** e não podiam ser removidos; “baú cheio” usava um `alert()` bloqueante.

…e os que os novos testes pegaram no código novo antes de publicar:

- Tooltips maiores que a tela podiam ficar **fora da tela** (teste unitário da matemática de posicionamento).
- Arrastar um orbe rápido **perdia o ponteiro** antes do primeiro evento de movimento (teste E2E de arrasto).
- Tooltips de elementos dentro de um `<dialog>` modal apareciam **por baixo dele** — a top layer vence qualquer `z-index` (E2E).
- A barra de ações fixa podia **cobrir o elemento focado** no celular (WCAG 2.4.11), descoberto quando o Playwright não conseguia tocar nele.
- Apertar Esc na carta ampliada **fechava a galeria inteira**: o React propaga eventos de um `<dialog>` aninhado para o pai (teste unitário).
- Limpar um storage adulterado **apagava o item duplicado plantado** antes que a caça aos bugs pudesse mostrá-lo (teste unitário do `normalize`).
- O axe apontou painéis com rolagem (registro de criação, diário de missões, relatório de QA) que **não rolavam pelo teclado**.
- A **varredura de pseudolocalização** encontrou textos que escapavam da camada de i18n: nomes de itens criados, rótulos de raridade e erros de criação (localizados por consultas diretas que a camada não via), as citações das recomendações, o nome acessível de um diálogo montado à mão e datas com nomes de meses vindos do `Intl` sem checagem. Agora tudo passa por ela; nomes, marcas e termos técnicos são marcados com `translate="no"`, como o HTML prevê.
- Um toast de conquista logo depois de outra mensagem **substituía a anterior na live region** antes do leitor de tela ler: "Item copiado" nunca era anunciado (teste de componente). Mensagens que chegam juntas agora são anunciadas juntas.
- Dados salvos corrompidos eram **redefinidos em silêncio**. Escrever o checklist de certificação deixou isso visível: um jogo de console precisa avisar o jogador. Agora ele avisa, uma vez, e descarta o valor ilegível.
- O teste de suspender/retomar primeiro **passava pelo motivo errado**: a animação de fundo também pausa sob qualquer diálogo aberto, e o teste tinha um aberto. Reescrito para checar cada metade separadamente, um lembrete de que um teste que passa ainda precisa de um caso que falhe.
- Dois novos botões na barra de topo faziam **"PT-BR" quebrar em duas linhas** a 320px (pego nos screenshots de celular).
- O novo **orçamento da thread principal** descobriu que cada criação custava 5× o trabalho de estilo devido: uma regra `:root:has(dialog[open])` (que pausa o fundo sob diálogos) fazia toda mudança no DOM dentro de um diálogo rechecar os estilos da página inteira. Agora o `<Modal>` marca um atributo na raiz: a sessão caiu de 34% para 29% de tempo na thread principal, o estilo das criações de 348 para 47 ms, e a taxa de quadros na CI subiu de 18 para 22 fps.
- A taxa de quadros na CI é limitada pelo runner: sem GPU, o Chromium compõe por software e até a ficha parada fica perto de 37 fps (uma página em branco: 60), enquanto hardware real roda na taxa de atualização da tela (144 Hz medidos). Por isso o Relatório de QA destaca o número que não depende de GPU, o tempo da thread principal por quadro (cerca de 5 ms de um quadro de 16,7 ms), e o mínimo de FPS é só um alarme.
- Uma execução instável do teste de rolagem horizontal era um bug real: **antes da fonte web carregar**, a fonte reserva, mais larga, empurrava os novos botões de recursos em duas colunas 9px além de uma tela de 360px. Corrigido, com um teste que bloqueia as fontes.
- O painel de dicas do controle, na camada superior, **engolia toques** nos recursos atrás dele no celular (um clique E2E estourava o tempo). Agora ele deixa os cliques passarem.
- O **botão do Resumo da Build não fazia nada no desktop**: um `.btn { display: inline-flex }` posterior vencia a regra que o escondia, e só o layout de celular tinha teste. Agora funciona em todo lugar, alterná-lo nunca move a árvore, e os dois layouts são testados.
- **Adicionar nós à árvore mudaria toda build salva**: os códigos eram uma máscara de bits na ordem em que o layout criava os nós, então um nó novo deslocava todos os bits seguintes. A ordem agora é fixa (`codeOrder.ts`), e testes decodificam códigos feitos antes de cada mudança.
- O Relatório de QA tinha **duas barras de rolagem**: textos só para leitores de tela, posicionados em relação ao `<dialog>`, o esticavam além da tela. Um teste agora abre todo diálogo e falha se algum rolar inteiro (verificado contra o bug).
- **Manual pontuava menos que Automação** mesmo com mais da árvore alocada: os atributos vinham só de alguns tipos de nó pequeno, então seguiam o layout e não a build. Agora todo nó do mesmo tipo dá o mesmo valor, garantido por um teste unitário.
- **O CI tinha parado de rodar sem avisar**: um `hashFiles()` num `if` de job fazia o GitHub rejeitar o arquivo de workflow inteiro, então toda execução "falhava" com zero jobs, o que parecia falha de teste. Descoberto ao investigar por que uma execução não tinha resultados.
- A primeira versão rodava a **4 FPS**. Um trace mostrou que ~95% de cada frame ia para rasterizar um canvas de tela cheia com brasas desfocadas; refeito com CSS que roda só no compositor, chegou a 60 FPS (e mover a árvore parou de re-renderizar o React a cada movimento do mouse).

## Por dentro

- **React 19 + TypeScript (strict)**, build com Vite, deploy no GitHub Pages via Actions.
- **Regras do jogo sem framework** (`src/game/`): puras, determinísticas e totalmente testadas. O React só renderiza.
- **Conteúdo como dados tipados** (`src/data/`) com inglês e português lado a lado; tradução faltando é erro de compilação.
- **Sem `innerHTML`.** O texto dos itens usa uma mini-marcação (`[valor]`, `{destaque}`, `((aviso))`) renderizada como nós React.
- **Recursos nativos da plataforma** no lugar de bibliotecas: `<dialog>` para modais (focus trap, Esc e fundo inerte de graça), Web Audio para efeitos sintetizados, animações CSS só no compositor para os efeitos, container queries para o inventário.
- **Toda entrada não confiável é validada**: links compartilhados e `localStorage` são lidos de forma defensiva; itens do baú são recriados a partir da receita, então um storage adulterado não gera item ilegal.

## Rodando localmente

Requer Node.js 20+.

```bash
npm install
npm run dev            # http://localhost:5173
npm test               # testes unitários, de propriedades e de componentes
npm run test:coverage  # com limites de cobertura
npx playwright install chromium
npm run e2e            # ponta a ponta + acessibilidade (faz o build e sobe o app)
npm run test:mutation  # Stryker na lógica do jogo → reports/mutation/mutation.html
npm run qa:report      # tudo acima + Lighthouse, e gera o relatório de QA do app
npm run og-image       # gera de novo o card de prévia de link (public/og-image.png)
```

Os testes visuais comparam screenshots com as referências de Linux em `e2e/visual.spec.ts-snapshots/`. Depois de uma mudança visual intencional, rode o workflow **Update visual baselines** (Actions → Update visual baselines → Run workflow, na sua branch): ele faz commit das novas referências para revisar no PR. Elas nunca são atualizadas automaticamente, porque um teste que aceita qualquer mudança não pega nenhuma.

Adicione `?pseudo` à URL para a pseudolocalização, ou `?perf` para o overlay de performance. Conecte um controle e aperte qualquer botão para jogar com ele.

### Alterando a “Minha Build”

Abra a árvore passiva → **Monte a Sua** → aloque os pontos → **Exportar código da build**, e cole o código em `MY_BUILD_CODE` no arquivo [`src/data/myBuild.ts`](src/data/myBuild.ts).

Adicionando nós à árvore: acrescente os ids ao fim de `CODE_ORDER_ADDED` em [`src/game/tree/codeOrder.ts`](src/game/tree/codeOrder.ts) (um teste unitário lista os que faltarem), para que os códigos de build existentes mantenham o significado.
